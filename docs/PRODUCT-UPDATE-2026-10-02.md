## 검증 결과

- Python 전체 회귀: 841개 수집, **838 통과 / 3 건너뜀**. 기존 하위 프로세스·Codex 프로토콜 가드 포함.
- 신규 Python 7개: 증거 표시·PID 재사용·로컬 요청 경계·체크포인트 차이·복구 기록 손상·실제 복구 검증.
- 프론트엔드: **13개 통과**, TypeScript/Vite 빌드 성공, lint 경고 없음. 세션 상태·종료 기록 유지·정렬·선택 항목 유지·모션 기본값 포함.
- CI Node 24에 프론트엔드 테스트를 추가했다. 기존 Node 20 상수 계약 테스트도 빌드·린트·테스트 실행 순서를 보장하도록 보완했다.
- `git diff --check` 통과.
- Windows `AIA.exe`, `aia-cli.exe` 빌드 성공. 패키지 `AIA.exe --server --port 8791` 기동·API·정적 자산 응답 확인.
- 별도 기록 폴더로 데스크톱 실행 및 해당 빌드 경로의 AIA 창 생성 확인. 네이티브 화면 캡처는 대상 창 대신 다른 화면을 반환해 렌더링 검증의 근거로 사용하지 않았다.
- 패키지 서버에 연결한 브라우저에서 정책 판정·비교, 도움말, 실제 파일 증거, 복구 미리보기, 복구 완료, 모션 감소, 작은 창 배치를 확인.
- 후속 소스 화면 검증: 종료 세션의 사이드바 유지·결과 이동, 가디언 도움말의 결과 이동, 전체 모션 선택 시 실제 CSS 변환 확인. 기존 자동 모드에서 브라우저가 모션 감소를 전달해 효과가 제한되는 원인을 확인했다.
- 최종 패키지 서버에서도 동일한 최신 정적 자산을 사용하며, 1,024px에서 가로 넘침 없이 세션 목록·세로형 가디언·증거 화면을 확인했다.
- 복구 시각 확인에는 `.tmp-build/product-ui-fixture`만 사용했다. 해당 폴더의 파일을 실제 변경·복원했고 `RESTORED / VERIFIED`를 확인했다. 실제 Codex가 실행한 시나리오로 포장하지 않는다.
- 기존 공용 pytest 임시 폴더의 실행 계정 권한 충돌은 새 테스트 전용 `--basetemp`로 분리했다. `CODEX_CLI_PATH`는 테스트 자식 셸에서만 제거했다.
- 기존 프로세스 센서 실패 테스트의 백그라운드 폴링 경합을 테스트 코드에서 제거했다. 센서 구현·실패 처리 규칙은 변경하지 않았다.

## 실행 파일

`dist/windows-guardian-pr/AIA/AIA.exe`

`AIA.exe`만 옮기면 실행할 수 없다. 같은 폴더의 `_internal`을 포함한 AIA 폴더 전체가 필요하다.
빌드 중 마지막 반응형 CSS를 보완해 최종 프론트엔드 산출물을 패키지 정적 자산에 다시 동기화하고 index 해시 일치를 확인했다.
재현은 저장소 루트에서 `powershell -File scripts/build-windows.ps1 -OutputRoot dist/windows-guardian-pr`로 가능하다.
기존 AIA 창이 떠 있으면 단일 인스턴스 기능이 이전 창을 앞으로 가져올 수 있다. 실행 중인 작업을 정상 종료하고 기존 창을 닫은 뒤 새 빌드를 실행한다. 임의 강제 종료는 하지 않는다.
설정 → 화면 모션에서 전체 모션을 선택하면 이 앱에서 움직임을 확인할 수 있다. 자동 모드에서는 운영체제의 접근성 설정을 따른다.
프론트엔드 테스트는 Node 24에서 `npm --prefix frontend test`로 실행한다.

새 빌드 경로를 사용하면 기존 Hook 경로·신뢰가 다시 확인되어야 할 수 있다.
설정 → 보호 연결 설정 → 설치 → Codex `/hooks`에서 검토·Trust → 연결 검증 순서다.
계정 인증·Codex 신뢰 설정을 이번 작업에서 자동 변경하지 않았다.

## 남은 제한·미완료 항목

1. 현재 생존 수는 등록된 프로세스의 PID·생성 시각 확인 결과다. CPU·메모리·명령행·OS 전체 프로세스는 이 표시 인덱스에서 수집하지 않는다. 200개를 넘거나 신원이 불확실하면 생존 수를 확정하지 않는다.
2. 파일 목록은 세션에서 관찰한 파일 이벤트다. 현재 파일 내용·파일 작성자·작업공간 밖 파일은 보여주지 않는다. 목록은 200개, 내부 파일 인덱스는 10,000개, 프로세스 인덱스는 5,000개로 제한된다. 큰 실행의 집계는 제한사항과 함께 봐야 한다.
3. 수동 복구는 **현재 작업공간 전체**를 기준점으로 되돌린다. 자동 사전 백업과 외부 작성자를 막는 원자적 트랜잭션은 제공하지 않는다. 미리보기 재검사는 외부 작성자의 모든 경합을 해결하지 않는다.
4. 복구 기록 체크섬은 손상·변경 감지용이며 디지털 서명이 아니다. 동일 OS 계정에서 파일과 체크섬을 모두 바꿀 수 있는 공격자를 방어한다는 주장이 아니다.
5. Origin·메모리 토큰 경계는 외부 웹페이지의 요청을 제한한다. Origin 없는 기존 로컬 CLI 클라이언트는 호환된다. 같은 PC의 악성 프로그램·다른 사용자를 인증하는 경계가 아니다.
6. Codex 대화 이벤트는 제한된 메모리 버퍼로 유지한다. 재연결 시 이미 제거된 출력은 복구할 수 없으며 누락 안내를 표시한다. 별도 Process Sensor가 수집하는 명령행은 원시 증거에 포함될 수 있다.
7. 현재 작업본으로 **실제 Codex 사전 차단 / 트리 중지 / 복구** 세 시나리오 반복 실행은 아직 완료하지 않았다. Fixture·기존 회귀 테스트만으로 최신 제품 실행 성공을 주장하지 않는다.
8. 다른 PC의 최초 설치·Windows Terminal 환경·WebView2 없는 환경·서명 릴리스 검증은 별도 필요하다. 자동 업데이트, 다중 에이전트 지원, 로그인, 소개 영상 제작은 이번 변경에서 완료하지 않았다.
9. 최신 버전의 실제 처리 지연·CPU·메모리·이벤트 누락률·큰 작업공간 성능은 새로 측정해야 한다. 과거 Fixture의 수치를 이번 빌드의 성능으로 재사용하지 않는다.
